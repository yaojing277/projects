2026-11-13（續）　整體狀態永遠是成功，而三個下游都在讀它排程靜默失效

需求：Jimmy 說「幫我重跑一次排程，測試看看」。目的是驗前一則的停牌修正， 但重跑的過程順便回答了一個更該問的問題：那三天失敗，為什麼沒有任何人被通知？

實作：查下去發現訊號一直在產生，只是被蓋掉。執行紀錄的逐步驟欄位三天都誠實寫著 最後一步失敗；但整體狀態與通知第一行都取自 CI 的 job 狀態，而所有會失敗的步驟都設成 「失敗不中斷」，CI 便把它們的結論記成成功——於是 job 狀態永遠是成功。
改法是新增一個彙總步驟：步驟清單在那裡產生一次，整體狀態由清單推導， 執行紀錄與通知共用同一份輸出。通知在第一行後附失敗步驟清單（正常日不會多這行， Jimmy 指定的行序不變）。

踩坑與解法：

  • 最貴的不是那個假值，是它有三個讀者。翻下游才發現三處都讀這個欄位， 而且三處都是照「它誠實」寫的：① 備援排程的註解明寫「主要觸發失敗時照跑，等於自動重試一次」 ——那個重試從未觸發過；② 本機觸發腳本的不重複觸發，失敗那天也被當成已完成而跳過； ③ 同一支腳本的漏跑警示刻意分「完全沒跑」與「跑了但失敗」，後者的條件是「狀態不等於成功」 ——那個分支永遠進不去。一個假值同時廢掉三個正確的讀者，而三邊都不會報錯。 📌 所以修法是只把這個欄位寫誠實，三個讀者一行都不用改；反過來去補三個讀者， 才是真正的治標。
  • 判定「不 OK」不要列舉失敗。第一版寫「挑出 failure 的步驟」，隨即改成 「不是成功也不是跳過」——這樣「取消」以及日後 CI 新增的狀態值會自動算進去。 列舉法的毛病是：沒被列到的狀態會安靜地算成成功，而那正是這一整則要修的病。 跳過刻意算 OK：它多半是上游失敗的連坐（上游自己已被記成失敗），或缺金鑰的刻意跳過。
  • 自己的檢查式先攔了自己一次。套補丁時我加了「改完檔案裡不該再有 job 狀態」的斷言， 結果被自己寫的註解觸發——新增的註解裡就在解釋「不可用 job 狀態」。 檔案沒被寫壞（斷言在寫檔前），把條件改成只找樣板語法。 📌 無害，但剛好示範了字串比對的檢查分不出「程式碼」與「談論程式碼的註解」。
  • 只在失敗日才會現形的亂碼。串接失敗清單原本用 paste -sd， 而它的分隔符是按位元組取用的：多位元組的「、」會被拆成三個分隔符輪流使用， 兩筆以上就吐出壞掉的 UTF-8。離線測四種情境時才看到那個替代字元。 而這條路徑只在出事那天才會走——真要等到那天，看到的是一則亂碼通知。改用逐筆串接。
  • 探測要打到真正會被擋的那個呼叫。正常路徑在雲端跑過一趟（整體成功、行序不變）， 但那完全沒有碰到失敗分支——而失敗分支才是這次要修的東西。 為此另建一個完全無副作用的測試工作流：不碰試算表、不寫執行紀錄、不推通知， 邏輯用程式從正式檔抽出而非手抄（手抄會與正式檔漂移，測到的就不是上線的那段）， 推到測試分支跑完即刪。

驗證結果：停牌修正本身：停牌那檔如期走進新分支、沿用停牌前收盤並印出警示， 四個分頁重跑後逐字相同（＝冪等），全紀錄無異常訊息。
⚠ 但要說清楚那證明了什麼：雲端與本機算出同一個市值，證的是部署版與本機版行為一致， 不是「這個數字對」——同源當然相同。數字的正確性是先前拿另一支腳本產生的 當日單日損益對過才成立的。
狀態修正：失敗路徑模擬「一步失敗＋一步取消＋一步連坐跳過」，結果整體判定失敗、 12 組步驟參數齊、取消算進失敗、連坐跳過不算、失敗清單無亂碼、 組成通知後是合法 JSON 並正確分成兩行，CI 介面也亮出警示。
📌 一天內三個 bug 同一個型態：一檔沒報價⇒非交易日、目錄在不在⇒repo 還能不能用、 job 狀態⇒整輪有沒有成功——都是拿「東西在不在」代替「它還能不能用」。

2026-11-13　一檔停牌，整個帳戶停更三天排程靜默失效

需求：Jimmy 問「今天排程有問題嗎」。整體狀態寫著成功，但逐步驟展開後， 最後一步連續三天 failure。

實作：順著查下去是一條四節的鏈：某檔 ETF 因分割而暫停交易 → 每日腳本抓不到它的收盤價 → 它的假設是「任何一檔取不到價＝今天不是交易日」， 於是整天什麼都不寫 → 下一步的防呆發現「每日表最新日期 ≠ 今天」而中止。
改成區分兩種情況：全部取不到才是非交易日（行為不變）；部分取不到判定個別停牌， 沿用停牌前最後收盤計入市值並大聲警示，其餘標的照算——與主帳戶既有口徑一致。

踩坑與解法：

  • 先看資料，再談機制。我沒有先去推論「是不是 API 限流／是不是憑證過期」， 而是直接拿交易所官方日線比對：同期間其他標的都有十筆、只有那一檔停在停牌日。 一次查詢就定案，不必碰任何機制層的猜測。
  • 「一檔沒報價 ⇒ 非交易日」這個假設，平常永遠是對的。 全市場休市時所有標的都沒報價，推論成立；它只在個別標的停牌時才垮， 而那是罕見事件——所以它可以安安靜靜地活很久，直到真的出事那天。
  • 防呆擋下來了，但沒人看見。下游那步的 --expect-date 發現日期對不上就中止不寫， 完全正確。問題是它被設成不中斷整輪，於是外層顯示成功、通知照推， 那道紅燈亮在沒有人會看的地方。📌 這和前一筆是同一個病的第三種型態： 容錯步驟吞掉失敗、腳本自己吞掉例外、以及這次——失敗有被記錄，但被成功的外層蓋住。
  • 失敗方向要刻意偏安全，並寫明偏哪邊。停牌期間部位的市值本來就不該變動， 所以沿用停牌前收盤是有依據的、不是硬湊；但那終究是估計值， 因此回傳值帶著停牌清單、log 大聲印出來。寧可記一筆標明「含停牌前價格」的資料， 也不要整個帳戶靜默停更三天。
  • 順手查到的另一個坑：分割不能提前登記。Jimmy 給了恢復交易日與比例， 我本來要先寫進分割表——讀了程式才發現換算只看「交易日 < 分割日」、不看分割發生了沒。 提前登記未來的恢復日，該代號既有買進會立刻被乘上比例，而價格還是分割前的， 於是冒出一個假的 N 倍部位。隱含前提是「只登記已經發生的分割」，原本沒寫下來，已補進設定檔。

驗證結果：三條路徑分開驗：停牌日算得出來並標示停牌； 週末仍跳過，行為未變；回歸對照取沒有參與這次計算的前一個交易日—— 分頁裡既有的值是舊版寫的，新版重算逐元相同。
補跑三天後，下游那步的雙向驗算比對 188 列、0 列不一致通過。
📌 同一輪還確認了一件舊帳：券商的逐筆淨收付截圖，與先前用完全不同來源反推的持股成本 四檔逐元吻合——兩個互不相干的來源同時對上，那批原本標著「僅供參考」的數字升格為權威值。

2026-11-08（續2）　抓取失敗兩個月，紀錄上全是綠燈LINE 通知靜默失效

需求：盤點近兩個月的 LINE 推送量時順帶發現：YouTube 新片通知兩個月推播 0 則， 而工作流程的執行紀錄每一次都是成功。

實作：逐一讀完九、十月 121 次執行的紀錄。失敗不是隨機的—— 排程遲到後實際約在台灣下午才跑的那一班幾乎每次回 404 或 500，晚上那班每次都成功。 同一個網址晚班與本機都抓得到，所以不是訂閱網址失效，是那個時段的暫時性失敗。
抓取改為兩個端點（頻道與其上傳清單，同一份資料的兩種查法）各重試四次、間隔遞增， 全部失敗才判定失敗並讓工作流程亮紅燈；判斷新片改用影片 ID 去重， 已推播清單由工作流程存回 repo，任何一班成功都會補推之前漏掉的。 推播失敗則不登記、同樣亮紅燈，下一班再推。

踩坑與解法：

  • 「推播 0 則」本身是對的，掩護了真正的問題。該頻道最後一部影片在八月底， 所以零推播完全合理——正確的結果讓人不會去查過程。 要是沒去讀執行紀錄，只會得到「沒新片而已」這個結論。
  • 真正的洞比抓取失敗更大，而且是看影片發佈時間才看出來的。 舊版只看「最近 13 小時」內的影片，而這個頻道幾乎都在台灣清晨上片—— 只有那個天天失敗的班次涵蓋得到那個時間窗。 兩個失效疊在一起才致命：就算真有新片，也會整部漏掉且不留任何痕跡。 📌 時間窗這種設計，「窗口剛好落在唯一會失敗的那一班」不會有任何徵兆—— 改成以影片 ID 去重之後，漏掉的下一班會自己補回來，窗口對不對就不再是單點故障。
  • 抓失敗只 print 然後 return，等於把紅燈改成綠燈。 舊版的例外被自己吞掉、結束碼 0，於是平台上兩個月的紀錄一路全綠。 📌 這和前一筆「容錯步驟把失敗吞成成功」是同一個病的兩種型態： 一個是工作流程層的設定，一個是腳本自己吞掉—— 判斷「有沒有真的成功」永遠不能只看最外層那個結論。
  • 404 被列入重試，是刻意違反直覺的。404 通常代表「不存在」、重試沒有意義， 但這裡有外部佐證：同一個網址在晚班與本機都回 200。 📌 決定可不可重試要看實測行為，不要看狀態碼的語意。 另外補了兩個防呆：沒有已推播清單時只推 48 小時內的片、超過 7 天的舊片一律不補推， 避免清單遺失那天把整頁歷史影片洗出來。

驗證結果：本機測過四種情境——正常、所有端點都失敗（結束碼 1）、 推播失敗（不登記且結束碼 1）、推播成功（登記且不重推）。 雲端手動觸發一次，紀錄顯示第一次就抓到 feed、判定沒有新影片。
⚠ 這次還驗不到最重要的那件事：真正要證明的是「下一次有新片時會推出來」， 而該頻道最後一部影片在八月底。要等真的有新片才算驗完—— 在那之前，能確定的只有「抓取失敗不會再是綠燈」。

2026-11-08（續）　規則寫在哪個檔案裡，那個檔案就沒被盤點到隱私公開頁

需求：專案設定檔長到每次對話都要整份載入，其中六成是一長串扁平清單—— 同一條教訓重複五六次，還混雜大量「當時怎麼查出來的」敘事。Jimmy 要求整理。

實作：重組後縮減約三分之一。九條最常被違反的判斷鐵律移到最前面 （驗證只能用沒參與推導的數字／先看資料再談機制／註解與程式不一致／探測要打到真正會被擋的呼叫／ 靜默失效比報錯危險／改了上游要查下游／掃描要掃三個維度／看起來成功不等於成功／失敗方向要偏安全）， 其餘拆成八個主題小節，「哪些口徑差異是刻意的」改成並列表格，散落各處的待辦集中成一張總表。
📌 之所以現在才敢壓縮，是因為前一筆把開發紀錄的四週空窗補完了—— 歷史脈絡有了去處，設定檔才能只留「該怎麼做」。分工確定了，才能動刀。

踩坑與解法：

  • ⚠ 那份設定檔本身也在公開的程式碼倉庫裡，卻從來沒被納入金額盤點的範圍。 前幾次清查把發佈頁掃了好幾輪、補了好幾種寫法，唯獨沒掃寫著這條規則的那個檔案。 它一度含有個人現金流與投資組合的絕對金額。盤點範圍要去讀發佈清單，而「規則住在哪裡」不等於「規則管得到哪裡」。
  • ⚠ 這次是壓縮順手清掉的，不是防線攔下來的。 那些數字之所以消失，是因為它們本來就屬於要刪的敘事——靠運氣不算防線。 所以把適用範圍明確寫進規則本身，並記下界線：「當下狀態」要清，「歷史問題的差額」可以留 （後者是特定問題的指紋，用來認症狀，不揭露部位規模）。 回頭掃線上頁才發現，先前那次清零本來就是照這條線做的——界線是還原出來的，不是我新訂的。
  • ⚠ 初稿把「哪些項目外洩過」逐項列了出來。 那等於替讀者指路，和「不要寫出怎麼用這些數字」是同一條—— 比數字本身更有用的是用法說明，而我差點把用法說明留在公開頁上。當天改成不列舉。
  • 刪東西要有機械防線，不能靠「我覺得都留著了」。 做法是把舊檔裡所有程式符號、分頁名、腳本檔名、記憶連結與觸發語抽出來逐一比對， 缺的一個一個判讀是「規則本體」還是「查案敘事」，規則本體全部補回。 順帶抓到三處過期內容：設定分頁名寫錯、一個數量統計停在舊值、認證方式的描述還停在舊做法。
